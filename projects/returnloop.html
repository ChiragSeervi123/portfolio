The problem

Most returned goods get refunded and written off. ReturnLoop grades every item at quality check and routes it to restock, refurbish or scrap, so value is recovered and every status change is on record.

It models the whole reverse-logistics loop of an e-commerce business. A customer asks to return an item, an agent picks it up, the warehouse checks it in, QC grades it, and the item is restocked, refurbished or scrapped. Then the refund is worked out to the rupee.

What it does

  • One app with six roles: customer, pickup agent, warehouse, QC inspector, refurbisher and admin, each with their own pages. After each step a handoff card passes the return to the next desk.
  • Return flow: request → pickup → warehouse check-in → QC grade A/B/C → restock, refurbish (then re-inspection) or scrap → refund.
  • Business rules kept in one config file: a 7-day return window; a refund of 100% for grade A, 70% for grade B once the repair passes re-inspection, and 0% for grade C; a ₹50 pickup fee only for “Changed my mind”; and a flag on customers with more than 3 return requests in 30 days, shown to the admin but never blocking the customer.
  • One state machine controls every status change and writes a history row each time, so every item has a full audit trail. The refund, the inventory log and the final status are saved in one transaction, so a second refund is impossible.
  • An animated QC “stamp” when an item is graded: the stamp slams down and the screen shakes (skipped with reduced motion).
  • An admin dashboard with Chart.js charts of return reasons and grades, and the list of frequent returners.

How it works

Scroll the diagram sideways →

Every move on this diagram goes through one function, change_status(). It checks the move against a transition table, writes a status-history row and updates the timestamp. Two side exits exist too: a return is Rejected as suspected fraud when QC finds the item doesn't match the order (unless the customer's reason was “Wrong item”), and Cancelled when the customer misses the pickup twice.

The app is Flask split into Blueprints, one per role plus a small JSON API. All business logic lives in services/, so the route handlers stay thin. Data is stored in SQLite through Flask-SQLAlchemy. Pages are Jinja2 templates with plain CSS and vanilla JavaScript: Three.js draws the 3D scenes, GSAP drives the landing-page scroll and Chart.js draws the admin charts. There is no npm and no build step.

The UML diagrams map straight onto the code: the use-case actors are the six roles, the state diagram is the state machine, the class diagram is the database tables, and the swimlane is the desk-to-desk relay.
