The problem

In small factories, friction, imbalance or cooling problems build up slowly. The motor keeps running but wastes energy, and nobody can tie the extra electricity bill to a specific machine.

Enterprise monitoring is too expensive for SMEs. And one fixed alarm threshold doesn't work across machines: a compressor, a pump and a lathe motor each have a different normal.

What it does

  • Retrofit kit design: an SCT-013 current clamp, an MPU-6050 vibration sensor, a DS18B20 temperature probe and a production counter on an ESP32 node, feeding a Pulse Edge gateway that buffers data when the network drops. The kit is designed and documented, but not yet built.
  • Tracks Specific Energy Consumption: energy per unit produced, not just total kWh.
  • Learns each machine's own normal baseline and alerts on sustained drift, not one fixed threshold. A deviation has to last before it counts, so short spikes are filtered out.
  • Explainable alerts: a “Why this status” panel shows each signal against its baseline, how far it has moved, and how much it weighed in the health score.
  • The simulator and the real sensor node feed the same analytics pipeline with the same packets, and every packet is tagged with its source.
  • A 3D twin of the motor in the dashboard, driven by the simulator's live values.

How it works

Scroll the diagram sideways →

Two sources of telemetry, one analytics pipeline. The simulator doesn't get its own analytics: its packets use the same format the ESP32 firmware would send. The FastAPI server runs every packet through the same chain: filter, extract features, compare against the machine's learned baseline, detect drift, estimate energy, then combine the signals into a green / amber / red health state with an action linked to the evidence. Results are stored in SQLite and pushed to the dashboard over WebSockets.

The analytics are deterministic, with no machine learning. An SME has no labelled failure history to train on, and an operator won't act on a number they can't question.
